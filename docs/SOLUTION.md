# 方案说明（SOLUTION）

## 痛点

招聘进展通常散落在企业微信群聊消息里（新增候选人、安排/改期面试、结果反馈、更正、退出等），
依赖人工逐条登记容易漏记、记错、难以追溯“为什么是这个状态”。本 Demo 针对该场景做
“消息 → 结构化事件 → 台账 → 展示与同步”的自动化记录。

## 方案

1. 接收模拟企业微信招聘消息。
2. 由大模型提取结构化招聘事件（候选人/岗位/渠道/负责人/阶段/面试/证据/不确定信息）。
3. 由代码（Harness）负责：Schema 校验、身份与应聘记录匹配、业务规则校验、去重、事务持久化、审计、待确认任务、同步任务。
4. 由 Streamlit 展示台账、面试安排、待确认事项、变更历史、看板与同步管理。

关键原则：**模型只负责“理解”，代码负责“校验与落地”**；模型输出未经校验不得写入业务台账。

## Harness 职责

- 去重（source + group_id + message_id）。
- 候选人/岗位匹配：姓名不能作为唯一标识；同名或同人多岗位无法唯一定位时创建待确认任务。
- 业务规则：未提及字段保留、明确清空、建议/否定/已安排/已完成/更正/退出区分、面试改期不重复创建、更正保留历史、相对日期按消息 sent_at + Asia/Shanghai 解释。
- 事务：业务事件 + 台账更新 + 同步任务同一事务；模型网络调用期间不持有数据库写事务。
- 同步执行器：单 worker，退避重试、幂等 upsert、超时恢复。

## 架构

```
app.py（Streamlit 五页面）
  └─ harness/  processor（消息处理）、dates（时间解析）、stats（看板）、syncer（同步）、demo_events（人工标注事件）
  └─ adapters/  模型适配器（Anthropic / Zhipu / Fake）、MockSyncAdapter（模拟外部表格）
  └─ storage/    SQLite 数据模型与仓储（含旧库安全迁移）
```

## 成本构成（不编造具体数字）

- 大模型调用按 token 计费（DeepSeek 实测：最小请求约 38 tokens、单条招聘提取约 1299 tokens；未折算金额，不编造成本）。
- 其余为本地 SQLite + Streamlit，无额外服务成本。
- 未接入 Redis / Celery / 常驻服务，单 worker 执行同步。

## 企业微信、腾讯文档正式接入所需条件

- 企业微信：具备消息接收权限的企微应用/机器人，配置回调或消息接口，获取群聊消息与发送人信息。
- 腾讯文档：开通腾讯文档开放平台应用，获取文档/表格读写授权（API 凭证），确定目标表格结构与字段映射。
- 两者均需真实账号、授权与接口密钥（仅从环境变量读取，不落库、不写日志）。
