# RecruitFlow AI 模拟数据包

全部人物、消息、组织和安排均为虚构，不含真实个人资料。未接入企业微信或腾讯文档。本包是开发与验收资料，不是已运行的 AI 应用。

## 文件与使用顺序

- fixtures/messages.json：唯一的业务输入；从空数据库按 deliveries 数组顺序逐条投递。
- fixtures/expected_results.json：人工标准答案，包含每次投递后的动作、变更、需保留字段、数量及完整业务快照，仅供评测程序使用。
- fixtures/expected_final_state.json：最后应有的台账、面试、确认任务及业务历史。
- fixtures/messages_preview.csv：便于人工查看的消息和答案对照表，UTF-8 BOM 编码。
- scripts/validate_fixtures.py：仅使用 Python 标准库，检查资料自身一致性。

运行：在本目录执行 `python scripts/validate_fixtures.py`。

**不得将 expected_results、expected_final_state 或 CSV 对照答案交给负责提取的模型。** 模型只能接收当前消息、发送元数据与系统当时已持久化的相关上下文。候选人和应聘记录从消息逐步创建，不预先导入最终状态。

## 固定业务假设

1. 时区 Asia/Shanghai，模拟时间为 2026-11-16 至 2026-11-17。日期固定保证重放一致，与程序运行当天无关。
2. delivery_id 标识一次投递；去重键为 source + group_id + message_id。D012 重复投递 M011，不新增业务事件、面试或同步任务；可单独记录技术投递日志。
3. C编号是候选人身份；A编号是应聘记录；I编号是面试。A/I编号只是标准答案的稳定标签，实际程序可使用其他内部ID，评测时按候选人编号+岗位、面试轮次建立映射。
4. 姓名不能唯一定位，同名即待确认。即使只有其中一人由发送HR负责，也不默认替用户做身份判断。
5. 同一人有多个岗位且原文未指定时待确认，不根据现有面试安排擅自推断。确认消息只执行被引用消息中、经本次确认消除歧义的操作。
6. 相对日期以原始业务消息 sent_at 为基准。M013确认M012时，“明天”仍按M012时间解释。
7. 新收到简历的记录默认新投递；“建议安排”不代表已安排；“二面时间待定”不创建二面记录。
8. 未提及字段不覆盖。expected_changes 是应聘记录的局部更新，expected_interview_after 是本次相关面试的完整预期状态，不能当作应聘字段。
9. expected_clear_paths 表示明确清空的字段，本组均为空；null仅表示该字段在相应快照中没有值，不能普遍理解为删除指令。
10. 一面结果消息将对应面试标为已完成；更正保留原始事件并改变当前结果。退出只取消待进行面试，保留原时间和面试官供追溯。
11. 业务历史采用“每条成功应用的唯一消息一个业务事件”。创建待确认任务、重复投递不计成功应用事件；确认消息计一次，并引用原消息。因此最终17个业务事件、2个已解决确认任务。
12. 此包未预设外部同步成功、模型准确率、延迟或成本；这些必须在实现后实测。

D007—D010：初筛、明确面试安排、仅建议安排。
D011—D012：一面改期和相同消息重复投递。

D019—D020：岗位歧义及确认退出，只影响后端开发。

## 评测边界与后续扩展

本组是带明确编号、固定业务假设的基础冒烟集，不证明真实群聊泛化能力。后续单独增加不带编号、跨天确认、闲聊、多人同句、多轮面试、明确清空、模型非法输出、乱序消息及同步失败等测试。不要用该答案集冒充模型提取实现。
